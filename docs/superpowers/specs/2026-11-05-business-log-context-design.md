# 业务日志上下文与有界生命周期设计

## 1. 目标与边界

代理请求、脚本执行是本项目的业务流程，结果日志必须能定位具体业务。上下文由集中事件适配层登记和读取，业务函数不再为日志逐次传入源地址、目标地址、代理配置或请求标识。

插件自身代码异常继续在已有 catch 中记录 String(error)，不要求业务上下文，不增加通用执行包装器。不是让任意位置的 logError(error) 自动识别当前异步请求。

本次范围为日志关联和结果记录机制，不改变代理行为、脚本执行语义、页面成功提示规则、日志设置及存储格式。

## 3. 已确认的约束

- 使用 Map + LRU，不使用 WeakMap。
- 统一日志上下文注册表最多 10000 条，代理和脚本共享这个上限，不是每种事件来源各 10000 条。
- 读取和更新命中项会刷新最近使用顺序，超限淘汰最久未使用项；正常结束立即删除。
- 不使用 Zone.js、AsyncLocalStorage、AsyncContext 或异步编译转换，不调整 Vite 的 async/await 处理。
- 不增加运行时依赖；复用 TypeScript、原生 Map、Chrome 事件、现有日志入口及 IndexedDB。
- 地址与修改后的请求头值按原文记录，不脱敏；不采集请求正文、响应正文、脚本正文或执行返回的数据。
- 不自动提交、推送、修改 .gitignore 或生成压缩包；构建仅运行 npm run build。
- 不自动创建子智能体；由当前主智能体执行设计审核。

上限是条目数，不是精确字节数。LRU 不是 TTL：缺少结束事件且没有新增压力时，条目可能继续存在，但不会超过 10000 条。本次不增加超时参数或定时扫描。

## 4. 方案选择

| 方案                                         | 取舍                                                     | 决定       |
| -------------------------------------------- | -------------------------------------------------------- | ---------- |
| 各日志点手动传全部上下文或创建 logger        | 调用重复，容易遗漏；不符合用户要求                       | 不采用     |
| Zone.js / 异步上下文传播                     | 可减少深层传参，但涉及原生 await、构建转换及扩展事件适配 | 本次不采用 |
| 浏览器事件 + 集中上下文注册表 + 单一结果归属 | 利用已有请求标识和执行入口，修改集中在适配层             | 采用       |

WeakMap 无字符串键查询、size 和遍历能力，不能独立满足精确容量和 LRU。用户已明确接受 Map + LRU 替代。

## 5. 结构与职责

1. context-registry.ts：保存有界上下文，管理 LRU、读取、替换、原子取走及按作用域删除；不操作 Chrome API，不写日志。
2. flow-logger.ts：登记业务上下文、根据流程标识生成统一结果日志、执行终止去重；继续调用现有 logInfo / logError。
3. proxy.ts：重定向事件适配器，复用原有监听器；不再另建一份无界的请求上下文 Map。
4. debugger-observer.ts：接收驱动已经监听到的事件和实际改写结果，关联 Network / Fetch，委托 flow-logger；不注册第二套竞争的 debugger 监听器。
5. script-execution.ts：集中处理现有脚本执行结果与上下文；不是包装所有业务函数的通用 try/catch 工具。

后台组合根只创建一个生产用 flow-logger，并注入代理观察器与脚本执行入口。测试可以创建隔离实例。日志工具不反向读取 UI store，也不依赖全局“当前请求”。

## 6. 上下文与标识

代理上下文保存：页签及调试会话作用域、原始请求地址、目标地址、命中代理的标识和名称、实际修改的请求头，以及确认改写和网络结束所需的有限状态。

脚本上下文保存：每次执行的独立标识、脚本标识、脚本名称、目标页签。无活动页签时不伪造 tabId；脚本执行失败日志可以明确目标不可用。

上下文是开始时的摘要快照，不能保存或修改整个 ProxyRule / Script 对象。更新只替换注册表中的快照，不改变输入对象。配置更名、切换或删除不能把旧请求的归属改成新配置。

标识规则：

- webRequest：来源前缀 + 浏览器 requestId。
- debugger：来源前缀 + tabId + sessionId + Network requestId；Fetch 的 networkId 存在时使用这一规范 key。
- 无 Network 标识的 Fetch 请求：独立的 Fetch 来源前缀 + tabId + sessionId + Fetch requestId。
- 脚本：脚本来源前缀 + 每次执行生成的唯一标识，而不是 scriptId。

不同 API 的同名标识不是同一个请求。Fetch / Network 的关联优先利用当前驱动已有 operation / requestOwners 中的 networkId，不增加无界别名索引、等待队列或已结束请求 Set。

只观察当前已生效规则实际覆盖的页签和调试会话；扩展自身补取资源的请求、不属于本驱动的调试会话不登记。配置应用通知需把当次已确认的页签作用域交给观察器，不能在请求结束时重新查询活动页签推断归属。配置通知可以增加可选作用域元数据，ProxyStrategy 接口和代理执行语义不变。

只有真正的流程开始入口允许登记；重定向后续事件、上下文补充、完成、失败事件仅查找已有项，查不到时不补建。适配器不能在每次 Fetch 暂停时无条件重新登记。

## 7. LRU 规则

- Map 的键按最近使用顺序排列。
- 新登记放末尾；同一活动 key 的重复登记保留初始归属，不覆盖成新配置，并刷新最近使用顺序。
- get 命中和 replace 命中均删除后重插到末尾；未命中不新增。
- take 先取得快照并删除，再返回；它是终止日志唯一的消费入口。
- 新增后超过 10000 条，移除队首，直到符合上限；测试可以注入较小容量，生产容量固定 10000。
- 按页签、会话、代理作用域清理不应把所有存活条目都标记为最近访问。
- 淘汰不改变代理执行、不取消脚本、不写“请求失败”日志。迟到的结束事件不补建、不猜测上下文，也不把淘汰误报成业务失败。
- 不另外长期保存终止快照、tombstone 或去重 Map。删除与未命中规则提供当前流程终止去重，不能用额外无界集合绕过容量上限。

有界状态不能提供无限历史去重：本次保证补充、完成、失败等后续事件不补建已淘汰条目，不承诺恢复淘汰前的整条事件历史。开始事件的重复/跳转判定在适配层处理，不通过永久保存已见过的请求 ID 解决。

容量约束只适用于日志关联状态；现有代理协议状态仍由驱动管理，不能为了日志 LRU 删除代理执行必需的状态。不得通过日志回调闭包继续强引用被淘汰的完整业务上下文。

## 8. 请求结果的单一归属

| 场景                                         | 最终结果记录来源      |
| -------------------------------------------- | --------------------- |
| 文档地址改写                                 | debugger 事件适配层   |
| 修改请求头或响应头的请求，包括先重定向再改头 | debugger 事件适配层   |
| 不涉及头改写的资源重定向                     | webRequest 事件适配层 |
| 未命中规则、只观察到匹配但未确认实际代理行为 | 不生成代理成功日志    |

两种代理不新增请求前后日志钩子，ProxyStrategy 接口保持不变。现有配置应用通知可以继续向观察器提供生效规则；它不是单个请求的开始/完成事件。

### 重定向

onBeforeRequest 登记候选上下文，onBeforeRedirect 核对实际源地址与目标；仅完成核对的链路，才在 onCompleted / onErrorOccurred 记录结果。后续跳转丢失归属时不能继续声称属于原配置。

### 文档与头改写

复用已有 debugger 事件入口，登记规则归属。实际命令成功后补充改写状态和 changedHeaders 的结果，不复制完整请求头。响应阶段不是完成；成功仍要求确认处理已应用且网络加载完成，事件先后交换也只能记录一次。

Fetch.responseErrorReason 和 Network.loadingFailed 可能报告同一个失败：第一个经确认的业务失败原子消费上下文，后续失败不重复写。暂停处理 finally 不能直接消费整个请求上下文。

若没有 networkId 且无法可靠确认网络完成，不伪造成功结果；在可观察终止或作用域清理时移除。此降级不能影响请求放行和页面错误提示。

## 9. 代码异常与业务失败

普通 logError 保持可用，现有代码错误不要求携带 key，也不承诺自动关联异步上下文。

改写命令自身拒绝：在集中 catch 中只写 String(error)，不要再单独拼代理上下文。若随后由插件主动 failRequest 或清理导致请求失败，先丢弃该日志流程，避免把人为终止再记成第二条业务失败。

真实浏览器网络失败由观察器记录；上层仅转发或展示同一个失败时不再 logError。独立的清理异常仍是独立代码错误，不按文字去重，不吞掉不同请求的相同错误。

showError 只负责错误状态和页签提示，不再隐式写业务日志。导航重新展示同一错误不得新增日志。取消、页签关闭、调试会话断开、停用代理只清理关联，不当作成功；用户主动取消不记为错误。

## 10. 脚本结果

前端 executeScript 消息增加 scriptId、scriptName，保留 code 仅用于执行。后台在现有执行入口登记每次调用；以 chrome.scripting.executeScript 的可确认结果为终点，记录后清理。用户脚本抛错或返回的 Promise 被拒绝属于脚本业务失败；插件自己的处理代码异常只记普通错误。

不得为了捕获用户脚本错误改变 MAIN 世界、注入函数序列化方式、执行正文、返回值结构或 Promise 等待语义。未返回的后台异步任务不在追踪范围。

前端收到已记录的失败回复只显示消息，不再写相同业务失败日志；消息传输失败等自身异常可继续记录 String(error)。非扩展开发模式不增加日志服务依赖，不能破坏现有 eval 路径。

## 11. 存储与可观测性

日志仍写入现有 LogEntry：message 直接描述业务事件，details 保存一次生成的上下文快照和错误字符串，不再以 Response replacement: 作为业务日志标题。

等级完整定义沿用当前模型：info 为普通运行信息，warning 为警告，error 为失败。代理和脚本成功使用 info、失败使用 error；取消和 LRU 淘汰不自动生成 warning。保存等级过滤只影响落库，不影响上下文终止和清理。

索引、日志保留期限、分页查看、导出、用户偏好 key 均不变。日志写入失败不能阻断请求、脚本执行或清理，不递归记录日志写入错误。

后台服务重启会丢失内存关联；本次不做在途请求恢复和上下文持久化，也不补造历史记录。

## 12. 验收标准

- AC1：代理和脚本共享的日志关联条目始终不超过 10000；LRU 读取/更新顺序正确，未命中不增加条目。
- AC2：请求真实失败日志能够定位原始源地址、目标地址和命中配置；实际修改的头值原文保留。
- AC3：并发请求、不同页签/会话的相同局部 ID、同一脚本并发执行不串上下文。
- AC4：重定向确认、头改写与加载完成正确关联；事件顺序交换不提前记录成功。
- AC5：同一失败由 Fetch/Network 或多个出口重复报告时仅一条业务结果；导航重报不重复。
- AC6：结束先生成快照再移除，日志失败也完成清理；取消、关闭、断开、停用、LRU 淘汰不影响业务执行。
- AC7：被淘汰后的更新、完成和失败不补建上下文、不重新匹配新配置；配置变更不污染旧快照。
- AC8：脚本成功、用户脚本失败有脚本身份；普通代码错误仅记录错误文本，不需要上下文或通用包装器。
- AC9：移除分散重复业务日志，但保留页面成功/错误提示、脚本响应协议以及日志管理功能。
- AC10：测试、类型、规范和生产构建通过；不引入异步上下文库、不改变构建目标。

## 13. 旧代码退出范围

实施时删除的是分散的业务日志职责，不是相关的整个条件分支。具体定位与验证清单见 plan 的“旧代码迁移与删除清单”。以下要求为强制验收项：

- showError 移除隐式 logError 及仅为落日志服务的 context 参数/缓存；保留错误消息、页签标题更新、清除及导航重报的展示行为。
- 请求失败、重定向策略拒绝、目标读取失败、文档加载失败分支不再拼装日志上下文；仍保留失败判断、暂停请求放行/终止、成功提示状态清理和 return/finally。
- 删除驱动内 logProxyRequest、仅写失败日志的 success.failed 回调及调用；保留通知的 begin/complete、applied/loaded 门控和必要的 successes 状态。
- getProxyErrorContext 在所有日志调用迁移后删除；不能据此连带删除驱动或新观察器仍需使用的 owner、requestOwners、networkRequests 等协议归属数据。
- 重定向旧成功/失败拼装与无界日志 pending Map 迁移到新机制；浏览器事件监听、实际跳转核对和清理继续存在。
- 扩展前端已收到后台脚本结果时不再重复记录；后台执行失败旧日志由新的集中业务结果替代。开发模式本地执行和消息传输错误不在“直接删除”范围。
- 移除 showError 的隐式写入后，原来依靠它记录的插件自身异常必须在集中 catch 显式记录 String(error)，不能把代码错误一起静默吞掉。
- 成功提示组件及其独立去重、取消、导航生命周期不属于本次删除范围。原生事件适配器、Map 清理和取消判断仍是必要代码，不能以“统一日志”名义消除。
